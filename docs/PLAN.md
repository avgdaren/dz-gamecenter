## 一、总路径

| 阶段 | 交付 | 目的 |
|---|---|---|
| **准备** | 源码基线、表结构、环境说明、协作文档 | 双方拿到同一个版本，接口核对完毕 |
| **v0** | 一款单机休闲游戏，完整接入 | 跑通「写代码 → 上架 → 登录打榜 → 服务端校验」整条链路 |
| **v1a** | 最小联机验证（五子棋） | 验证实时同步、身份校验、并发写入能不能站住 |

## 二、v0 · 单机接入（按「最快能验证」定题）

**选型：4×4 翻牌记忆配对（memory）**

理由：规则极简、一个文件能写完；洗牌由开局 `seed` 完全决定，`verify.php` 能彻底重放，是验证「服务端校验」这条链路最快的题材。

### 关于作弊面的已知结论（必须写清楚，别自欺）

**只要 `seed` 在前端，任何确定性游戏都能被脚本完美游玩**——翻牌能算出全部牌面，2048 一样能算出后续块位置。**换题材解决不了这个问题**，这是平台架构决定的。

所以 v0 的处理方式：

- **不发积分**（后台每局奖励填 0），排行榜只作展示；
- `verify.php` 只负责证明「客户端不能直接指定分数、非法操作过不去」；
- **不把 v0 的排行榜当作真实竞技排名**。

### 验收标准

- [ ] `gkey` 合法、目录结构合规，后台「重新扫描」能登记
- [ ] 大厅卡片能显示（名称/简介/图标），点进去能玩
- [ ] 桌面 + 手机都能玩（触控、宽度自适应、不横向滚动）
- [ ] 游客能试玩但不记成绩；登录后成绩入库
- [ ] **服务端校验生效**：手改分数 / 乱传数据被退回
- [ ] 正常连玩 10 局无误判
- [ ] 成绩窗口正确：分数、个人最佳、本周名次
- [ ] 排行榜三个 tab（今日/本周/总榜）数据正确
- [ ] 控制台无 JS 报错
- [ ] 未修改 Discuz 核心、无 npm 依赖

## 三、v1a · 最小联机验证（五子棋）

实现细则、升级与回退见 [V1A-GOMOKU.md](V1A-GOMOKU.md)，执行任务 Issue #6。

### 规则范围

15×15 自由五子棋；连五及以上获胜；**不做禁手**；满盘无胜者判和。
房间号/邀请加入，房主执黑，第二人加入即开局。保留认输。

### 架构（不可商量）

- **服务端权威状态机**：棋盘、轮次、回合截止时间、结果全部在服务端，前端只提交落子意图、只做渲染。
- 身份从服务端已验证的论坛会话取，**客户端传的 UID 一律不认**。
- 传输：**短轮询**，默认 2 秒，不短于 1.5 秒，加小幅随机错峰；页面不可见时停轮询，回到前台立即同步；错误退避；同一页面最多一个请求在途。
- 落子请求带**预期版本号 + 请求标识**：重复请求返回既有结果（幂等），过期版本要求同步。
- 同一回合只生效一次：InnoDB 事务 + 行锁（`SELECT ... FOR UPDATE`）或带版本条件的原子更新。用 `DB::begin_transaction()`。
- 超时判负与有效落子必须在**同一并发保护范围内**判定，避免两者同时成立。

### 验收标准

- [ ] 两个账号（或浏览器 + 手机）能完成一整局
- [ ] 刷新页面 / 切后台再回来，能接回原局
- [ ] 一方超时能正确判负
- [ ] 伪造落子（改前端、直接发请求）被服务端拒绝
- [ ] **两人同时落子 1000 次：只有一次生效、无死锁**（InnoDB 死锁 1213 要能自动重试，不许抛给玩家）
- [ ] **截止时间前后 ±200ms 打 200 次落子：「超时判负」与「有效落子」互斥**
- [ ] 未修改 Discuz 核心

### 容量验收（阈值已按实测校准，见 §五）

- [ ] 40 个已登录页面持续轮询 10 分钟（约 20 QPS）
- [ ] 轮询 p95 **≤ 150ms**
- [ ] 同期普通页面 p95 ≤ 无负载的 1.5 倍，且增量 ≤ 200ms
- [ ] 零 5xx、零超时、php-cgi 进程内存不持续增长

## 四、v1b · 可验收的联机版本

- 独立的对局记录表（**现有 `gamecenter_best` 是「每人每档只留最佳」，塞不进对战结果**）
- 结算去重：一场对局只有一个最终结果；刷新/重试/清理任务都不重复发积分
- 玩家下线后也能完成或补偿结算（不能靠玩家再开页面）
- 展示胜/负/和与最近对局；对战排行统计口径单独定义，**不硬塞进单机最高分榜**
- 房间生命周期与清理（配合 Discuz 计划任务；安静时段靠请求触发按服务端截止时间给正确结果）
- 移动端完善

## 五、容量基线（2026-10-26 本机实测，供阈值校准）

| 配置 | 瞬时并发 20 | 持续 10 QPS × 20s |
|---|---|---|
| php-cgi 单进程 | 墙钟 328 ms | 未测 |
| **php-cgi 4 workers** | 墙钟 **149 ms**（p50 98 / p95 128） | **p50 37 / p95 53 ms**，零错误 |

同 UID 并发（真实登录态）：游戏中心页 p50 49 / p95 64 ms；论坛首页 p50 29 / p95 44 ms；持续 5 QPS p95 51 ms。**未观察到会话锁阻塞。**

> 因此 p95 ≤ 150ms 是留了约 3 倍余量的阈值；不要用「≤500ms」那种松阈值，测不出问题。

## 六、明确不做（别扩）

- ❌ AI 对手、人机对战
- ❌ 自动匹配算法（先用房间号/邀请）
- ❌ 观战、聊天、悔棋
- ❌ 积分押注或任何额外货币
- ❌ 通用游戏引擎、微服务、预建抽象层（第一版都在插件内实现）

## 七、长期方向（本次不做，仅记录以免把路堵死）

论坛管理员的规划：单机小游戏 → 在线竞技棋牌 → 共同冒险动作游戏 → 2D 线上小广场（互相可见、可对话）→ 借鉴关服网游的美术与玩法。

**架构预警**：第 3、4 条需要 100–300ms 级位置同步与多人同屏，PHP 短连接 + 轮询走不通，将来要换成独立的实时服务（如 Node.js + WebSocket），Discuz 只保留账号与积分。

所以 v1 请**刻意把状态机与 Discuz 解耦**（状态读写集中在独立接口层，账号只依赖 `uid`），将来能整块搬走。
