## 1. 这一步要交付什么

下一次实现交付应是一份可在真实浏览器操作的几何原型，以及能够在 PHP 中重算同一份输入的规则程序。先回答两件事：基础弹型是否可读、操作是否顺手；连续弹幕的重播成本是否适合现有论坛。

P0 包含三个独立的 45 秒弹型练习场、键盘与基础触控、自动射击、生命／清屏、碰撞／擦弹、暂停／恢复、输入导出与 JS/PHP 差分检查。场景中 Boss 暂不以血量结束战斗，只统计命中和伤害；自然终点为生命耗尽或 45 秒结束。

标准三阶段的血量、时间与组合节奏在本稿同时写清，供 P1 直接接续；P0 不承担完整三阶段战役、正式计分榜、论坛接入、美术或音轨制作。

P0 原型只提供测试预览入口，不在大厅扫描登记，不修改既有游戏。PHP 的原型入口只供本机命令行和测试使用，不提供可公开调用的回放接口。

Boss 轨迹的准确起相：令 `u=(a-1) mod 480`。定点横向偏移依次为：u<120 时 `4096×u div 120`；120≤u<360 时 `4096-(8192×(u-120) div 240)`；其余为 `-4096+(4096×(u-360) div 120)`。将偏移加到 `240×64`，即得到当步 x。所有括号内除法均为非负整除。

自机用浅蓝箭头，Boss 用有明确外轮廓的大圆，敌弹按弹型采用不同形状与描边。危险实体与柔光分层，柔光不计碰撞。背景保持低亮度。正式角色形象在 P1 可玩战斗成立以后再定。

## 3. 输入细节

| 操作 | 桌面 | 触控 |
|---|---|---|
| 移动 | 方向键／WASD；相反方向同时按下则该轴为 0 | 单指相对拖动；手指可落在角色旁边 |
| 慢速 | 按住 Shift | 固定位置的慢速开关 |
| 清屏 | X 或空格，按下沿触发 | 独立按钮，单次按下触发 |
| 暂停 | Esc／页面按钮 | 页面按钮；触控中断自动暂停 |

逻辑按 60 步／秒推进，坐标精度为每像素 64 个整数单位（Q=64）。正常位移上限每步 256 单位，即每秒 240 像素；慢速上限每步 96 单位，即每秒 90 像素。v0.1 中 100 像素／秒是候选，本稿改为可整步表达的 90。

键盘水平／垂直位移分别是 ±256 或 ±96；斜向每轴采用 ±181 或 ±67，按归一化后向内取整，不能因斜向移动更快。少量量化误差不做额外速度补偿。

触控适配器把拖动转换成逻辑目标位置，再逐步向目标移动；每步位移量化成整数，并约束 `dx²+dy²≤速度上限²`。松手即停止，不保留惯性；指针取消、失去捕获或页面失焦时清空输入并暂停。两指操作可分别负责拖动和清屏，不让清屏按钮夺走移动指针。

键盘事件只在游戏获得焦点且玩家未编辑输入框时接管。暂停中按 Esc 可继续；后台返回不直接继续，必须确认并经过界面倒计时。暂停及恢复倒计时不产生游戏逻辑步，不写入回放。

逻辑不依赖显示刷新率；高刷屏不会多走步。渲染积压时单次最多追赶 5 步，仍落后则自动暂停，不能跳过逻辑步、加快逻辑速度或少生成子弹。

## 4. 三个弹型的精确定义

统一方向角使用 0～511 的整数，0 向右、128 向下、256 向左、384 向上，按顺时针增加。方向表在实现时离线生成并随规则版本保存：对角度 θ=2π×角度编号/512，向量为向 0 截断的 `(1024cosθ,1024sinθ)`，并核验四个主轴及向量长度不超过 1024。两端载入同一份表，不各自重新计算。运行时速度分量为 `速度定点单位×表分量 div 1024`，负数除法统一向 0 截断。

有效战斗步 `a` 从 1 开始。12 秒循环的循环号 `c=(a-1) div 720`，循环内步 `q=1+((a-1) mod 720)`。所有敌弹出生当步就移动，寿命 480 步；最后一个有效寿命步仍可碰撞，其后回收。飞出场地四周 32 像素后回收。

### 4.1 星环：旋转花瓣

- 首发在 a=60，此后每 90 步发射一次。
- 每轮原始 32 个方向，方向为 `旋转偏移+i×16`，i=0～31。
- 不发射 i=6、7、8、9、10，实际每轮 27 颗，在朝下区域留下宽缺口。
- 第 n 轮从 0 开始，旋转偏移循环取 `[-16,-8,0,8,16,8,0,-8]`，缺口缓慢左右摆动。
- 出生点为当步 Boss 中心；速度每步 96 个定点单位，即每秒 90 像素；实体半径 5。
- 预期动作：观察缺口，小幅跟随；慢速修正，不要求持续大幅绕场。

每颗弹自身做匀速直线运动，“花瓣”来自多轮方向偏移，不做复杂曲线。P0 先验证清晰度与路线，再考虑是否需要改造弹型。

### 4.2 星雨：瞄准连射

- 每个 720 步循环，在 q=60 时读取一次自机和 Boss 位置，锁定一个瞄准方向。
- 用目标向量与 512 个方向表向量的点积选最大值；并列取角度最小者，不使用运行时 atan2。
- q=60～89 显示不伤人的瞄准预告；q=90、108、126 各发射一组。
- 每组 5 颗，方向相对锁定方向偏移 `[-16,-8,0,8,16]`；三组共 15 颗。
- 每次从当步 Boss 中心出弹，但方向始终使用 q=60 锁定值，不追踪玩家；速度每步 160 单位，即每秒 150 像素；半径 4。
- 预期动作：先让敌人瞄准旧位置，再离开原路线。不能把提示线画成已经生效的伤害线。

### 4.3 星幕：交错波浪

- 每个循环 q=360、450 各启动一批；每批在启动后第 0、18、36 步各出一排。
- 每排原始 9 列，基础 x 为 `[24,78,132,186,240,294,348,402,456]`，y=112。
- 三排分别整体偏移 x=-12、0、+12。
- 批次编号 `n=2×c+b`，b 为循环内第 0／1 批。缺口起始列 g 循环取 `[2,3,4,3]`，省略第 g 和 g+1 列；同一批三排使用同一个 g。
- 每排 7 颗，每批 21 颗，每循环两批共 42 颗；竖直向下，速度每步 128 单位，即每秒 120 像素，半径 6。
- 预期动作：先判断缺口位置，再横移穿过；三排偏移制造变化，但不会突然让某一排转向。

P0 三个场景分别只启用对应弹型，固定运行最多 2,700 步（45 秒）。星雨／星幕场景的长空隙保留，用来观察弹幕到达和恢复节奏；不能用单项场景的刺激程度推断组合关卡已好玩。

## 5. P1 三阶段如何拼成一局

P1 才启用下表的完整战斗，但这些参数已足够供实现接续。

| 阶段 | 血量候选 | 编排 | 设计目的 |
|---|---:|---|---|
| 星环 | 4,500 | 使用花瓣单项规则 | 识别判定、学习微调 |
| 星雨 | 4,800 | 同一 12 秒循环中，前段瞄准连射，后段交错波浪 | 学会诱导，避免停在原地 |
| 星幕 | 5,100 | 下述 12 秒组合循环 | 在持续弹幕中选择换位时机 |

第三阶段每循环安排：q=60／180／300 发射花瓣；q=360／450 发射波浪；q=540 锁定瞄准，q=570／588／606 连射。

第三阶段花瓣只省略 i=7／8／9，即每轮 29 颗，速度改为每步 128 单位；第 n 轮偏移仍沿用花瓣序列，n=3×c+循环内轮号。波浪每排只省略 g 列，即每排 8 颗，速度改为每步 160 单位。连射每组 7 颗，偏移 `[-24,-16,-8,0,8,16,24]`，速度改为每步 192 单位。其余半径、寿命和时点语义不变。

完整标准局：开场 180 步；每阶段最多 4,200 步，击破即结束当前阶段；两次转场各 120 步。开场可移动，禁止射击和清屏；转场清除双方子弹、保持自机位置和剩余资源，可移动，不射击、不消耗清屏。每阶段 Boss 轨迹和弹型局部时钟重置，生命与清屏不重置。

最大实际逻辑长度为 `180+3×4200+2×120=13020` 步，即 217 秒；13,200 步是解码硬上限，其余 180 步是预算余量，不作为可继续游玩的时间。终局后不允许附加输入。

自动射击理论上每秒 100 伤害；忽略首弹飞行时间和转场清弹，三阶段全命中约 45／48／51 秒，合计 144 秒。按 80% 有效命中率估算为 56.25／60／63.75 秒，合计 180 秒，加开场与转场约 187 秒。该估算只证明血量与时长目标大致相容，不证明真人能稳定达到 80% 命中率；70 秒超时是否过紧要在试玩中确认。

## 6. 每步结算顺序与边界

每个有效战斗步严格执行：

1. 保存各对象上一步位置，读取一条输入并按场地边界移动自机。
2. 按既定轨迹移动 Boss；根据当前有效步生成自机子弹、敌弹，或锁定瞄准预告。
3. 推进所有子弹。新生成子弹的旧位置是出生点，禁止从画面外虚构扫掠路径。
4. 应用当步清屏：若有库存则扣一次，移除全部敌弹，设置无敌截止步。
5. 检查自机命中；每步最多扣一命。扣命后移除所有本步命中的敌弹及距新自机位置 48 像素内的敌弹，并设置受击无敌。
6. 自机生命为 0 立即失败，跳过本步输出／击破／擦弹；仍存活则结算自机子弹对 Boss 的有效伤害。
7. Boss 血量归零则击破／转场或通关，清场后跳过擦弹与阶段超时。截止步击破有效。
8. Boss 未击破，若阶段时间到则失败；否则在非无敌状态下结算擦弹。P0 单项场景在同一顺序下以时间到完成场景。
9. 回收超寿命／越界子弹，生成本步状态摘要；终局后停止所有逻辑更新。

命中关系使用相对运动的线段到圆距离，包含等号，覆盖玩家与子弹同一步内交错穿过。双方圆半径相加；擦弹检测半径为 18+敌弹半径，且必须未命中。每颗敌弹只有一个 `grazed` 标记，首次合格后置为真，重复靠近不再给分。

无敌采用截止步语义：在 t 步触发 N 步无敌，则 `[t,t+N)` 内有效。受击 N=120，清屏 N=90；已有无敌与新无敌取较晚截止步，不缩短旧无敌。无敌时不进行擦弹记分。清屏库存为 0 时操作无效，不制造假清屏或无敌。

窄相位碰撞前必须做扫掠包围盒排除，剩余运算使用整数点积／叉积，不开平方；两个对象相对静止时单独处理零长度线段。Q=64 下仍须按实际最大坐标、速度和半径复核所有中间值小于 JS 安全整数上限，不能只因最终结果很小就认定安全。

Boss 与自机不做身体接触伤害，活动区域已分开。自机子弹对一个 Boss 只命中一次，命中即移除，不能穿透重复计伤害。有效伤害不得超过剩余 Boss 血量。

## 7. 计分公式补全（P1 使用）

三阶段总血量 14,400。有效伤害累计为 D，擦弹合格颗数为 G，已击破阶段数为 B；通关标志 C 只能取 0／1。通关剩命 L、剩余清屏 Z 都来自模拟结果。A 为三个阶段累计有效战斗步数，不含开场、转场、暂停或界面倒计时。

`分数 = C×200000 + B×20000 + (min(D,14400)×20000 div 14400) + min(G,1000)×10 + C×(L×2000+Z×1000+时间奖励)`

`时间奖励 = min(10000, max(0, (12600-A)×100 div 60))`

即相对 210 秒总阶段预算，每提前 1 秒约多 100 分。所有乘法先做、最后整除；时间奖励仅通关时计入。失败局最多击破两个阶段，其总分必低于通关底分 280,000；308,000 是保守数学上界，不表示存在同时拿满各项的实际路线。

P0 只显示命中、有效伤害、生命、清屏和擦弹统计，不提前模拟一套与 P1 不同的正式积分。辅助练习永不提交正式成绩。

## 8. 回放格式：先简单、可审计

每个逻辑步固定记录 5 字节，按步顺序紧密排列：

| 字节 | 含义 |
|---|---|
| 0～1 | dx，有符号 16 位整数，小端；单位为 1/64 像素 |
| 2～3 | dy，同上 |
| 4 | 标记：bit0 慢速，bit1 当步清屏按下沿；其余位必须为 0 |

记录的是移动意图，不是客户端位置。服务端先校验速度圆约束，再按场地边界限位。bit1 只表达本步释放意图，按键是否一直按住由前端适配；恶意记录连续多次释放也只能消耗真实库存，不能增加资源。

输入全为 0 也必须有记录。原始记录 Base64 编码后提交，严格拒绝多余字节、无效字符、非零保留位、非法步数和长度不等于 `5×ticks` 的数据。Base64 不做压缩；解码前先验总字节数，避免不受限分配。

13,200 步恰为 66,000 原始字节，Base64 为 88,000 ASCII 字节。连同版本、终点和分数，远低于 256 KiB 的游戏级上限，最坏逐步触控变化不会使记录膨胀。

P0 本地导出包含：`prototype=true`、场景 flower／aim／wave、是否辅助、规则 ID、ticks、input；本地结果／状态摘要单独保存作对照。P0 PHP 入口仅接受明确的原型场景，不能伪装成正式 verify.php。

P1 标准提交规划为 `{v, rule, ticks, input, score}`；平台开局凭证与 seed 沿用原契约。标准规则不接受原型场景或辅助参数，终局、血量、资源和分数均由 PHP 重算。首版编排固定，seed 不改变弹型，不额外制造难度随机性。

规则 ID `danmaku-p0-r1` 仅用于原型；冻结标准版本时另设正式 ID。公共接口字段名称与契约不变，以上字段只属于本游戏的提交数据。

## 9. 弹量与资源预算

| 场景 | 不依赖实际出界回收的保守在场上界 |
|---|---:|
| 花瓣 | `(480 div 90+1)×27=162` |
| 瞄准单项 | 每组循环 15 颗，寿命不足覆盖相邻连射组，最多 15 |
| 波浪单项 | 每个循环 42 颗，同型相邻循环的生成窗口间隔超过寿命，最多 42 |
| 第二阶段组合 | 更宽松地按两个完整循环估算，最多 `2×(15+42)=114` |
| 第三阶段组合 | 每循环 `3×29+2×3×8+3×7=156`；寿命 8 秒短于循环 12 秒，按两个完整循环估算最多 312 |

敌弹在场硬上限 360；整局累计出生硬上限 4,096。三个阶段均按最长 70 秒逐步枚举发射时点，总出生量为 1,269+342+929=2,540，仍留余量。自机子弹在场上限 32，按每 6 步一次、寿命 90 步，宽松估算不超过 16 颗。

2026-11-10 已执行一次独立的规划算术核对：只按发射时间和寿命枚举，不计算出界／清屏／碰撞清弹，三个阶段的在场峰值分别为 162／57／135。另核对了最大逻辑步数 13,020、输入 88,000 字节、斜向不超速、参数 JSON 可解析及文档内部文件链接存在。该脚本没有调用游戏引擎，不能证明游戏实现正确、可通关或性能达标。

上限是规则约束，不是渲染降质开关。表现降质可以少画光晕和粒子，不能丢敌弹、改变碰撞或根据帧率调整规则。超过设计上限应报告规则错误，禁止安静地删弹后继续记成绩。

P0 性能筛查分两类：真实规则下导出的正常记录；另设 360 颗常驻弹、13,200 步的引擎压力夹具。压力夹具需要绕过寿命或终局条件，明确标“非合法标准局”，不作为实际通关路线或正常局不误拒的证据。最长合法完整标准局与真实通关回放在 P1/P2 补验。

PHP 计时先预热 5 次，再测同一最重夹具 50 次，记录 p50／p95／最大值和峰值内存，初始 p95 目标≤500ms。记录 PHP 版本、CPU、CLI 配置及测试脚本版本。CLI 只是筛查；四路提交对普通论坛页面的影响属于 P2 实际 HTTP 测试，不能用 CLI 数据替代。

## 12. 进入 P1 的判断

P0 交付必须有可操作预览、源码版本、规则／参数版本、正常操作回放、跨语言结果、压力夹具说明和性能报告。每一项列出实际执行命令与结果；未运行的保留“未验证”。

可以进入 P1 的条件：三个基础弹型可读，命中原因能复核；键盘和基础触控不失控；同一输入跨语言一致；资源与回放体积满足上界；性能筛查达到预算或已定位并修复超预算原因。

允许后续调的是弹速、间隔、缺口、Boss 血量与命中率目标。若修改更新顺序、输入含义、碰撞或规则参数，须更新规则 ID 和对应回放，不把新规则偷偷应用到旧记录。
