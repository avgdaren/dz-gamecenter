## 1. 产品定位与范围

面向天使动漫论坛的轻量回合制合作讨伐。推荐两位会员邀请组队；一位会员也可直接开局，以高于双人合作的难度挑战同一只首领。手机和电脑都通过点击选择行动完成战斗。

用户已确定的约束：玩法区别于翻牌记忆和五子棋；有二次元气质；美术投入集中；单人必须存在通关办法；最新目标为比双人难“2–3 个点”，作为体验目标，保留可学习和调整策略的空间；先做可玩战斗样稿，再投入首领插画。

| 首版交付 | 明确范围 |
| --- | --- |
| 游戏 | `gkey=raid`，暂名《天使讨伐令》 |
| 内容 | 一只首领“蚀月魔女 · 幽月”，两个强度阶段，固定可学习的行为循环 |
| 模式 | 单人挑战 / 双人合作，开战后人数与模式固定 |
| 行动 | 攻击、守护、恢复；守护和恢复可用于自己或队友 |
| 成长 | 每局独立初始状态，无跨局属性成长 |
| 记录 | 单人/双人标签、胜负、用时、回合数、生还人数、最近 10 次个人结果 |
| 美术 | 一张静态首领插画，图标从该图派生；玩家使用论坛头像 |
| 联动 | 论坛账号、好友邀请、恢复与通关记录；首版积分奖励为 0 |

首版不包含职业、装备、背包、掉落经济、抽卡、大地图、自动匹配、聊天、观战、AI 队友、复活、全服排行榜和实时动作同步。合作仅限两位真人，倒地玩家可看本房间结果。通关标签只在本游戏展示，不新增论坛勋章系统。

目标体验时长：双人约 2–4 分钟，单人约 3–5 分钟，属于待试玩验证的目标。每轮最长 30 秒、最多 16 轮，活动战斗逻辑截止上限 480 秒；无人访问时可延迟落库，恢复访问后按原截止时间追算。等待好友最长 5 分钟，另计。

## 2. 玩家流程与协作方式

1. 游戏页显示“独自挑战（高难）”“邀请好友”和“加入房间”，提供无需登录即可阅读的规则说明。
2. 实际开局需要论坛登录及参与权限。单人创建后直接准备第 1 回合；双人房主创建等待房间，将房间号/链接交给好友。
3. 好友点“加入并开战”，服务端占第二座并开始第 1 回合。打开邀请链接只显示加入入口，不自动占座。
4. 每轮先显示首领预告及目标，玩家选择行动、必要时选择自己/队友，再确认。确认即锁定，服务端接收后显示给队友。
5. 队友能看到“已确认：守护你 / 攻击 / 恢复自己”等信息，再补足另一项行动；首版不依赖额外聊天功能。
6. 全体存活成员确认后立即结算；否则到截止时间，为未确认者填入“守护自己”后结算。
7. 结算展示本轮摘要、血量变化及下一轮预告；胜利或失败后提供“再挑战一次”“最近讨伐”。双人重开创建新邀请房间，不自动把队友拉入。

一位玩家每轮只操控自己一个角色。单人模式没有第二个可操控席位。战斗中不补位、不换人、不改变模式或首领数值。

## 3. P1 战斗规则与固定数值

首领展示名已按用户第二轮定案统一为 **蚀月魔女 · 幽月**。名称和台词只在展示层使用；`balance_check.py` 与 `P1-REFERENCE.json` 保持字节不变。开场：`你选择一人面对魔女，还是和伙伴一起挑战魔女？`；第二阶段单人：`你惹怒我了！`，双人：`你们这群蝼蚁！`。胜利沿用 `这一次，算你们赢。下次可没这么轻松。`，失败沿用 `别急着认输。记住这轮月光，再来一次。`。

根据用户本轮定案及 [PR #9 数值留言](https://github.com/avgdaren/dz-gamecenter/pull/9#issuecomment-6418945175)，固定 P1 基线为 `raid-v1-p1-balanced`：单人 120 首领生命/3 次恢复，双人 130/每人 2 次。原 `raid-v1-baseline` 和 `raid-v1-p1-solo3` 保留作历史对照。此后不再以“数值待拍板”阻塞 P1；真人难度与手感仍需样稿验证，调整时同步升级规则版本与对照文件。

| 参数 | 数值与约定 |
| --- | --- |
| 每位玩家最大/初始生命 | 40 |
| 首领最大/初始生命 | 单人 120；双人 130；创建时由服务端按固定 mode 生成 |
| 普通攻击 | 10 点伤害 |
| 破绽期攻击 | 20 点伤害 |
| 守护 | 指定一名存活成员，本轮对该目标的首领伤害变为 `ceil(原伤害 / 5)`；不叠加 |
| 恢复 | 单人 3 次、双人每人 2 次；每次为指定存活成员恢复 28，至多 40；消耗施放者的次数；开局按 mode 固定，不随倒地改变 |
| 第二阶段 | 准备新回合时 `boss_hp * 2 <= boss_max_hp` 即进入：单人 ≤60、双人 ≤65；已发预告保持不变 |
| 回合上限 | 16；第 16 轮完成后首领仍存活即失败 |
| 随机性 | 首版伤害、目标、行为均无随机命中或暴击 |

设定文案为“首领基础生命 120；双人挑战获得月蚀加护，生命 +10”。该加护只对应开局总生命 130，不新增独立护盾条、吸收层或护盾破碎机制。两种模式使用同一首领与素材。首领上限、恢复预算、mode 在开局固定；双人一人倒地/离场后仍为上限 130、阶段阈值 65，不能改为单人 120 或补发第三次恢复。

所有数值使用整数。生命为 0 的成员不能行动、不能恢复、不能接受守护；尚存活的队友可继续战斗，首领数值不随倒地减弱。至少一名成员存活并击败首领即为全队胜利，同时记录生还人数；不会向玩家承诺每位成员都生还。

### 3.1 首领循环与目标

每四轮重复下表。以 `c=floor((round-1)/4)` 表示循环编号，座位从 0 开始；双人点名目标为 `c % 2`，每个循环轮换一次。单人始终点名唯一玩家。被点名者已倒地/离场时，在准备回合时改为另一存活成员，并公开新预告。

| 循环位置 | 行为 | 第一阶段 | 第二阶段 | 应对意义 |
| --- | --- | --- | --- | --- |
| 第 1 轮 | 月刃，点名一人 | 8 伤害 | 10 伤害 | 决定承受伤害输出、守护或恢复 |
| 第 2 轮 | 星潮，全体 | 每人 8 | 每人 10 | 两人需要分别考虑自己的血量；守护队友不会同时保护自己 |
| 第 3 轮 | 蚀月重击，点名一人 | 24 | 28 | 守护后分别为 5 / 6；队友可代为守护，让被点名者继续攻击 |
| 第 4 轮 | 回气，不攻击 | 0 | 0 | 上轮成功守护重击则本轮露出破绽，否则仅普通回气 |

“成功守护重击”：重击实际结算时，点名目标受到守护且结算后仍存活。对应下一轮所有成员的攻击均为 20；恢复等行动不会延长破绽。破绽只维持这一轮，不储存、不叠加。重击回合直接击败首领时，战斗已经胜利，不再产生下一轮。

预告必须写明行为、受击者、原伤害、守护后的伤害。玩家本轮把首领打入半血，不会让已经公告的伤害临时增强；新阶段在下一轮准备时生效。

### 3.2 严格结算顺序

1. 按本轮已公布的预告、开始状态和已锁定意图验证行动；倒地者无需提交。
2. 建立守护目标集合。多人守护同一目标只形成一层；施放者没有自动获得自己的守护。
3. 消耗恢复次数并同时应用恢复。目标生命封顶 40；确认时已满血的目标不可选择恢复。同轮多人恢复同一受伤目标均消耗各自次数，溢出不保留，界面要提示避免重复。
4. 汇总玩家攻击并扣首领生命；首领归零即胜利，本轮首领攻击取消。
5. 首领执行预告，对受击者应用守护减伤；生命降至 0 则倒地。全员倒地即失败。
6. 处理重击是否产生下一轮破绽、回合后离场；若无人继续或达到 16 轮仍未击败，结束并给出原因。
7. 否则准备下一轮，公布新阶段、目标、截止时间。状态、意图消费和摘要在同一事务中保存。

恢复次数只在结算阶段扣除，接口重放不再扣除。失败的输入验证不占本轮行动。玩家行动先于首领，允许最后一击抢在致命重击前结束战斗。

## 4. 已定 P1 基线与演算证据

运行 `python3 docs/raid/balance_check.py`。仅 Python 标准库，无网络/数据库连接；默认规则为已定的 `raid-v1-p1-balanced`。保留旧版对照，追加 `--trace` 可导出逐轮状态。

当前 **45 项核对通过**。选定单人数值有 **574 条合法通关序列**，最早第 14 轮，所有通关中的最高剩余生命为 30。所测稳健策略第 16 轮获胜，剩 14，恢复 3 次用尽；双人掩护仍第 6 轮胜，剩 19/22，不用恢复。

“所测稳健策略”：重击轮先守护自己；其他非回气轮，生命 ≤20 且有次数则恢复，否则攻击；回气轮攻击。阈值改为 ≤24 的结果相同。它是明确的可复现策略，不代表全部合理打法。

记号：`A` 攻击、`G` 守护自己、`H` 恢复自己。空格只分组。

**P1 体验目标：** 单人明显更难，同时允许看懂预告、安排恢复、调整策略后通关；双人能体验掩护和援护的收益。目标差距按用户最新“高 2–3 个点”执行，须以不看答案的试玩、一次迟交后的应对、失败原因可读性及二次挑战改善来判断。数值已定为 P1 起点，实际手感尚未验收。

## 5. 联机、时间与异常行为

- 传输继续使用约 2 秒 + 0–250ms 错峰的短轮询，正常间隔不低于 1.5 秒；隐藏时停轮询、恢复立即同步、错误退避至 15 秒、单页仅一个请求在途。前端倒计时只显示，结算由服务器决定。
- 每轮 30 秒。截止前全员存活成员已提交，按收齐时刻结算；截止时尚缺的意图为守护自己，无恢复消耗。
- 行动与截止竞争：在房间行锁内读取服务端时间。`now >= deadline_ms` 时先到期结算，再处理请求；旧回合行动拒绝。不能拿请求进入 PHP 的时刻绕过已经到期的锁内时间。
- 超时结算的逻辑时刻为原 deadline；下一截止为该时刻 +30 秒。早齐结算则下一截止为实际结算时刻 +30 秒。恢复访问不重新获得整轮思考时间。
- 请求触发可连续追算到当前时刻，最多 16 轮、一次有界处理。没人访问时不保证准点写库；可接入现有 Discuz 计划任务清理到期房间。
- 超时仍默认守护自己；不采用“空过且无守护”，因为它仍损失输出，并额外失去减伤和可能的破绽触发。单人恢复预算提供生存决策空间，不宣称解决所有超时。持续离线不输出，最终失败；服务端不操作攻击或恢复来替玩家通关。
- P1 试玩后的 P2 首轮策略：保持 30 秒硬截止，不新增暂停／续时；连续 2 个已结算回合未确认时，提示具体席位与连续次数，并给出继续等待或本人单方撤退的入口。不把未确认说成已离线，不自动踢人或转单人；倒地／正式离场不计挂机。下一次确认后清除连续提醒。双人撤退仍在本轮结束后生效，不需队友批准；数值保持开局模式。等待大厅 5 分钟取消后需显示邀请已过期、允许重建，并验证资格释放及旧链接拒绝。依据与角色设定候选、P1 表现层补充见 [试玩反馈处理](raid/P1-PLAYTEST-RESPONSE.md)。轮询只影响显示延迟，不给迟到请求额外时间；真实手机双人若需要更长思考时间，另升级规则版本与时间预算。
- 已提交的动作不能改选。同一 request_id / 同一请求内容重放返回原确认和最新快照；同 ID 不同内容拒绝。网络结果未知时沿用同 ID 重试，先同步再决定新操作。
- 双人一方倒地，剩余成员继续；倒地者不再阻塞回合，不允许刷新复活。成员名单、模式和初始血量保持原值。
- 单人撤退立即结束为失败。双人撤退显示二次确认：“本回合结束后离场，队友将继续挑战”。已确认动作仍执行；尚未行动者锁定守护自己；该轮结束后标记离场。离场者不能返回操作，剩余成员继续原双人挑战。全员离场记失败。
- 等待房间允许房主取消。开战后没有取消胜负的入口；终局不可再加入、行动或重复结算。首次终局状态及结果不会被迟到请求覆盖。

## 6. 页面与最小美术清单

主屏自上而下：首领图与血条 → **当前预告及受击目标** → 两位玩家头像/生命/恢复次数/已确认行动 → 三个行动按钮与目标选择 → 确认按钮 → 最近一轮摘要。完整日志默认折叠。

手机 320/390 宽可完整操作；行动按钮点击区域至少 44×44 CSS 像素。选择守护/恢复时默认自己，队友目标以头像+昵称+血量明确标识。提交前完整显示“守护某某”或“为某某恢复”；确认后显示锁定状态与剩余时间。无次数/目标满血/已倒地等不可用原因直接说明。

键盘支持 Tab、Enter/Space；本游戏不接管整页方向键。血量与目标通过数字、文字和边框共同表示，不只依赖颜色。提供减少动态效果、关闭音效，尊重系统 reduced-motion。离线或重连时保留权威快照，等待确认，不先演出扣血。

`raid_rules.php` 只接收结构化状态、意图与时间，不读取论坛全局或执行 SQL；服务器权威计算。JS 只用于输入、显示和演出，不决定胜负。纯规则及模型使用相同规则版本，未来新增首领时再依据实际需求扩展。

## 8. 数据与接口约定

### 8.1 三张新增 InnoDB 表（实现时写 DDL）

| 表 | 主要字段与索引 |
| --- | --- |
| `gamecenter_raid_room` | id；唯一 code（12 位大写十六进制）；creator_uid/name；slot0_uid、slot1_uid；唯一(creator_uid,create_request)；mode；rules_version；status；round_no；version；deadline_ms；state_json；result_json；created/updated/ended_ms；expiry(status,deadline)、creation_rate(creator_uid,created_ms)、slot0_history(slot0_uid,updated_ms,id)、slot1_history(slot1_uid,updated_ms,id) |
| `gamecenter_raid_member` | uid 主键；room_id 指向最近房间；room_id 索引；每 UID 最多一间活动讨伐房 |
| `gamecenter_raid_action` | 主键(room_id,uid,request_id)；fingerprint；action；round_no；规范化参数；accepted_version；created_ms；索引(room_id,round_no) |

`state_json TEXT NOT NULL`，使用 utf8mb4，应用层对编码后 JSON 做 `strlen <=16384` 字节校验；不用数据库 JSON 类型或 JSON SQL 函数。内容包含固定 mode、首领上限、成员/座位、生命、剩余恢复、每轮意图、当前预告、破绽、离场标记、最后已结算轮及最多 16 条回合摘要。每条摘要上限 512 字节，仅保存座位/枚举/数值，不重复昵称、头像 URL 或长文案。

`result_json TEXT NOT NULL`，应用层限制 4096 字节，创建时显式写入 `{}`，终局只保存结束摘要，不复制所有回合日志。应用层使用 JSON_THROW_ON_ERROR 编解码并检查 schema/version/字段范围；解析损坏时失败并记录内部错误，不静默变成空状态。名称长度、数组项数及字节数均限定，SQL 参数绑定。

成员 UID/昵称来自会话，目标只传房间座位；服务端核对真实成员。初始人数、规则版本、各项数值均由服务端配置生成，客户端不能指定。

记录读取通过 member 指针及 room 表的 slot0_uid / slot1_uid 检索；JSON 与列在同一事务写入，单人 slot1_uid=0。分别按 `slot0_uid=uid AND status>=2` 和 `slot1_uid=uid AND status>=2` 查询，各自 `ORDER BY updated_ms DESC,id DESC LIMIT 10`；PHP 以 room id 去重、按相同顺序排序取前 10 条，避免对 state_json 内 UID 做全表搜索。采用两次独立查询，不拼 SQL UNION：Discuz 默认 querysafe 的 unionselect/unionall 会拦截 UNION。两个分支各取 10 足以组成合并后前 10；P2 另验分页/同时间排序与 EXPLAIN。房间代码不是访问权限，第三人不能读取成员、血量或行动快照。

房间状态固定为 `WAITING=0 / ACTIVE=1 / WON=2 / LOST=3 / CANCELLED=4`；`raid_member.room_id` 在终局后保留最近房间，不统一清零。创建/加入时，在指针和旧房间锁内先追算到期，只有状态为 WAITING/ACTIVE 且本人成员尚未正式离场时才报 active；终局、已不存在的房间或已正式离场不阻塞新开，成功后将指针更新为新房间。倒地但仍留队的成员继续占用该活动房间，直至终局或正式离场。

双人撤退在本轮结束、离场状态落库后释放本人的活动资格；新的 `current` 可仍显示最近一局并标记不可操作。旧房间后续终局/清理不会覆盖玩家指向新房间的指针；旧 create 请求重放只返回原房间回执，不把指针改回旧房。不能用 `room_id != 0` 判断“仍有活动房”。

讨伐与五子棋的成员指针独立；首版不实现跨全部游戏的活动房间互斥。创建/加入时先锁自己的 UID 指针，再锁关联房间，沿用固定锁顺序。事务前确认三张讨伐表在同一物理连接。

### 8.2 请求

统一入口：`POST plugin.php?id=gamecenter&game=raid&op=raid&inajax=1`，包含 formhash。输入最多 4KB，值只允许标量；code/request_id 等与五子棋采用相同格式约束。

| action | 参数 | 语义 |
| --- | --- | --- |
| create | mode=solo/duo, request_id | 单人直接开战；双人等待；重放恢复同一创建 |
| join | room, request_id | 只允许一个第二成员；同账号不能占两座；重放不重复占座 |
| current / state | 无 / room | 成员恢复当前/指定房间并追算到期 |
| act | room, round, kind=attack/guard/heal, target（攻击固定 -1）, request_id | 每位存活成员本轮只能锁定一个意图 |
| retreat | room, request_id | 按 §5 离场，不自动重开或改变模式 |
| cancel | room, expected_version, request_id | 仅房主取消等待房间 |
| history | 无 | 本人最近 10 次终局摘要；单/双人分别标识 |

响应含 ok/code/msg/server_ms、成员可见 snapshot、request receipt。snapshot 包含规则版本、状态、mode、round、version、deadline、玩家状态、首领与预告、已确认意图、最近摘要；请求回执保留 accepted_round/version，重试时可能已进入后续回合。服务端内部 SQL/异常不回显。

**act 按 round 校验，不要求两个玩家持有相同的全局 version。** 第一位锁定动作会改变 version，第二位仍可向同一未结束 round 提交；同一 round 同一座位的不同请求只允许一个成功。version 用于快照更新和取消等待房间。避免照搬五子棋的单方轮次条件导致双方互相冲突。

### 8.3 原子性、规则版本与限制

房间行锁内依次完成：成员验证、幂等记录查询、到期追算、本轮行动验证/写入、是否收齐、结算与终局保存、回执写入；一次事务原子提交。请求 ID 指纹包含 action / round / kind / target 等全部语义参数。每个回合只结算一次，结算本身不依赖“谁的响应先显示”。

使用 DB::begin_transaction/commit/rollback；1213/1205/唯一键竞争有限重试；事务禁止自动重连重放，锁等待 ≤2 秒后恢复原 session 设置。读取设置使用 SHOW SESSION VARIABLES，不能再次使用 SELECT @@SESSION。DB 测试必须开启官方默认 querysafe，并有原拦截查询的失败哨兵。不得修改核心安全检查或添加 SQL 白名单。

客户端超时 10 秒后显示未确认状态，同 ID 重试；终局/回合追算同样保持幂等。规则版本在创建时固定；部署新规则不得静默替换未结束房间的规则，需保留活动版本处理器。未知前端版本先要求刷新。

创建频率沿用每 UID 10 分钟最多新建 30 间；终局不能靠重放创建刷一场新局。每个房间最多 16 回合，行动记录正常上限约 32 次 + 少量生命周期请求；对无效或重复提交不新增无限日志。

## 9. 记录、升级与回退

结算页显示：胜利/失败及原因、单人挑战/双人合作、首领规则版本、回合数、生还人数、双方生命与恢复次数、本局摘要；个人最近 10 次结果可回看。标签对应“创建模式”，双人中一人倒地后获胜不记为单人讨伐。不同规则版本/模式不混排，首版没有新的全服榜或积分结算。

实现版需完整部署插件并升级新建三张表；不能只复制 games/raid。原 9 张表不 ALTER。DDL 可重复执行、不清空已有记录；新增表使用正式安装/升级入口，不在前台请求中建表。

回退：备份代码与数据库 → 关闭 raid → 处理/取消未结束讨伐 → 恢复上一版插件与对应版本元数据/缓存 → 保留新增三表及记录。**回退不等于卸载插件；卸载会删除全部插件表。** 回退演练在独立测试库执行，不使用真实成绩验证删表。历史自动删除与长期归档不在首版；先估算上线后数据量，再单独制定保留政策。
